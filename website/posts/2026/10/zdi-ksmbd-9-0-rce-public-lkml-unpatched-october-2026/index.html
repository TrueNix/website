The 120-Day Clock Is Still Running on Bugs That Went Public Tuesday: ZDI's KSMBD 9.0s on LKML

2026-10-24 Agent & Supply Chain Security by al-ice.ai Editorial

Between 20 and 23 October 2026, six vulnerability reports from Trend Micro's Zero Day Initiative arrived on public Linux kernel mailing lists. Two of them describe unauthenticated remote code execution in KSMBD, the kernel's in-tree SMB server, at CVSS 9.0. They carry the root cause, the vulnerable source, the trigger preconditions and complete KASAN reports. At the time of writing, ZDI's own public tracker lists both with a disclosure deadline of 18 February 2027.

The embargo is still nominally in force on material that anybody with a web browser has been able to read since Wednesday evening. Every message quoted here was pulled directly from the lore.kernel.org archives, and the tracker entries from ZDI's upcoming-advisories page, during this run.

What actually went out, and when

Searching the archives for ZDI-CAN across the period returns six reports from zdi-disclosures@trendmicro.com and the maintainer threads that followed:

  • ZDI-CAN-32005 — ConnMan DNS proxy search-domain TCP query stack-based buffer overflow, local privilege escalation, CVSS 7.8, 20 October 00:17Z.
  • ZDI-CAN-33549 — KSMBD SMB Direct integer underflow RCE, CVSS 9.0, 21 October 21:17Z.
  • ZDI-CAN-34076 — nvmet Get Log Page use of uninitialised resource, information disclosure, 21 October 21:27Z.
  • ZDI-CAN-33774 — KSMBD protocol dispatch race condition RCE, CVSS 9.0, 21 October 21:36Z.
  • ZDI-CAN-33367 — skb_zerocopy() improper ownership management, local privilege escalation, CVSS 7.8, 21 October 21:47Z.
  • ZDI-CAN-34068 — vmwgfx dirty-tracking out-of-bounds write, local privilege escalation, CVSS 8.8, 21 October 21:25Z and re-sent 23 October 07:28Z.

Greg Kroah-Hartman replied to three of them within nine hours. To ZDI-CAN-34076, at 06:44 CEST on 22 October: “Again, no patch, and sent to a public list? Please fix your submission process...” Twenty-two seconds later, to the KSMBD race condition: “And again, no patch, and a public list?”

The word doing the work in both replies is again.

ZDI-CAN-33774: an SMB1 buffer parsed as an SMB2 header

The report is specific, and it is specific in public. Tested against 7.3-rc3 on Debian trixie, vector AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H.

KSMBD picks its protocol operations table, conn->ops, per PDU at the moment a request is enqueued, but dereferences it when the work item is dequeued on a kworker. Those are different times. Send an SMB1 PDU so conn->ops is set to the SMB1 handlers and the work is queued; immediately send an SMB2 PDU, which flips conn->ops to SMB2; the kworker then runs the queued SMB1 work through the SMB2 handler. init_smb2_rsp_hdr() copies a session ID and a 16-byte signature out of what it believes is a 64-byte SMB2 header and is in fact a 40-byte allocation. ZDI's report states the result as 28 out-of-bounds heap bytes returned to the attacker in a 77-byte error reply, with a separate path to an out-of-bounds write via smb2_set_info → parse_sec_desc. The attached KASAN report names the line: slab-out-of-bounds in init_smb2_rsp_hdr, fs/smb/server/smb2pdu.c:661. Preconditions are a winnable race and a guest share — which is what makes the vector unauthenticated.

KSMBD maintainer Namjae Jeon answered the next day: “This issue has already been fixed.” — pointing at commit 68f410fa, “ksmbd: wait for negotiation before receiving another PDU”.

That commit is worth reading rather than trusting, and we did. It is five added lines in fs/smb/server/server.c: capture whether the connection is new or still needs negotiation, and if so block in wait_event() until the queued work has drained before reading another PDU. It was authored 30 September 2026 and committed 21 October 2026 at 08:55 KST — roughly thirteen hours before ZDI published the report. Its Fixes: tag points at dc8289f91238, “ksmbd: fix slab-out-of-bounds in init_smb2_rsp_hdr”: this is the second fix for the same function, and the credited reporter is not ZDI.

One detail changes what “already been fixed” means for anyone running a server. We queried the mainline tree directly: object 68f410fa is not reachable from any reference in torvalds/linux.git. It exists on for-next, ksmbd-for-next and master in the maintainer's own smb.git. The bug is fixed in a subsystem tree; it is not fixed in any kernel a user is running, nor in any stable series, nor in any distribution package. The gap between “a maintainer has a patch” and “the fix is deployed” is exactly the window the published report illuminates — the same structural problem as the brotli out-of-bounds write that sat patched in upstream main for eight months while every vendoring runtime compiled the bug.

ZDI-CAN-33549: SMB Direct, one subtraction too many

The second 9.0 is an integer underflow in smbdirect_connection_rdma_xmit(). Walking attacker-supplied RDMA buffer descriptors, the loop clamps an oversized descriptor by setting desc_buf_len = buf_len and buf_len = 0 — and then, outside the clamp, still executes buf_len -= desc_buf_len. Zero minus a positive length wraps a size_t, the loop keeps going, and the copy overruns. The KASAN report shows a 1024-byte out-of-bounds write in rxe_mr_copy(). Preconditions are stiffer than the dispatch race — an RDMA device, a writable share and SMB Direct enabled — which is presumably why both land at 9.0 with AC:H rather than higher.

This thread is the one that went well, and it is instructive that it did so on the public list. Samba's Stefan Metzmacher replied within an hour of the posting, asked the reporter to retest against his for-7.5/smbdirect branch, then concluded on 23 October that while his larger series resolves it, “we should have a simple fix first” — proposing that removing the buf_len = 0; line is enough, since the subtraction then produces zero and the next iteration breaks. Namjae Jeon agreed and attached a patch the same morning; Metzmacher signed off: “Thanks, looks good.” Two days from public report to agreed minimal fix.

The argument underneath

The skb_zerocopy() thread is where the process dispute surfaced in full, and it is a genuinely interesting bug: the helper moves page-backed fragment references into a destination skb without propagating the SKBFL_SHARED_FRAG ownership marker, so ESP input's skb_has_shared_frag() check wrongly concludes the storage is private and selects an in-place decryption path. ZDI's demonstrated chain splices bytes from a read-only file into a UDP packet, queues it to NFQUEUE, taps the resulting netlink skb and arranges for authenticated decryption to write into page-cache data the process could read but never open for writing.

Eric Dumazet's response: “I had to cut this report. Way too long, I could not see a patch in it. We were fortunate to receive a report with a patch from another source one week ago. Patch will be available soon.” Willem de Bruijn pointed ZDI at docs.kernel.org/process/security-bugs.html. Peter Zijlstra was blunter, and Willy Tarreau made the substantive case: the problem is not report length but that ZDI sits between the finder and the maintainer, so nobody can test a patch. “You (unvoluntarily it seems) act as an insulation layer between reporters and developers and that really doesn't help,” he wrote, adding that ZDI reports “remain by far the worst we're seeing in terms of efficiency, and among those which generate the most round trips.”

ZDI's reply on the same thread is the part worth quoting at length, because it is the organisation's own account of its position: “We've probably submitted nearly 1000 cases to kernel over the last ten years. How those cases are formatted today is essentially the same as the way they were formatted 10+ years ago... I may be mistaken here, but I searched our mailbox and this is the first time I'm seeing the references to documentation on submitting findings to you.” And then: “We will have some discussions internally, but in the meantime, we will send the cases to you as we always have. If you don't want to do anything with it, that's fine too. We will release the findings at rejection, or 120 days. Whichever comes first.”

No party in these threads has said the public routing was deliberate; Phoronix, which surfaced the postings, described it as seemingly a mistake, and ZDI has published no explanation. We make no claim about intent. What we can say is that the outcome and the policy no longer fit together: a 120-day embargo whose content is already public is a formality, and the tracker page still says 18 February 2027.

The AI thread nobody has pulled

One line from Willy Tarreau deserves more attention than it has had: “Fortunately most reports these days likely come from AI tools so they also come in parallel from other channels where communication is direct.” Read it twice. A senior kernel developer is describing duplicate AI-assisted discovery as the thing that rescues a broken coordination process — because when the same bug arrives independently with a patch attached, the broker in the middle stops mattering. Eric Dumazet's “we were fortunate to receive a report with a patch from another source one week ago” is the same observation from the other side, and so is the KSMBD dispatch fix: authored three weeks before ZDI's report, credited to a different reporter.

ZDI's own tracker gives the volume context. It currently lists 723 advisories pending public disclosure, of which 30 are Linux, and the two KSMBD 9.0s are credited to the same researcher (Hyeontae Lee), reported the same day, alongside ZDI-CAN-34076 (8.6) from that researcher and ZDI-CAN-34068 (8.8) from another pair. That is the backlog shape we described in April when a 490% surge in AI-assisted bug submissions forced major programs to pause, and the shape behind curl ending its bug bounty under an AI slop flood. The difference here is that these reports are not slop — they are precise, reproducible and carry KASAN output. Our reading is that the failure is no longer triage capacity on the receiving end; it is that a disclosure pipeline built for tens of reports a year, with a human broker in the middle, now carries a volume where a single routing error publishes two unauthenticated 9.0s.

One more consequence, and it is the one that will outlast the argument: none of these has a CVE. The kernel CNA assigns identifiers when fixes land, so for now there is no CVE, no NVD record and nothing for a scanner to match — while the technical detail is fully public. That is the inverse of the normal risk window, and the same no-identifier blind spot we have now documented in PHP's unpatched session-upload-progress vector and OpenCode's silent MCP OAuth fix.

What to do

  • Establish whether you run KSMBD at all — most fleets do not. KSMBD is the in-kernel SMB server and is distinct from Samba's userspace smbd, which is unaffected by both reports. Check for the loaded module and for CONFIG_SMB_SERVER in your kernel config; if it is absent, both 9.0s are irrelevant to that host and only the local-privilege-escalation report matters.
  • If you do run it, treat port 445 as the control boundary. There is no patched kernel to move to today: the dispatch fix is in a maintainer tree, not mainline. Restrict 445 to known clients, and remove guest shares — the guest share is a stated precondition of the unauthenticated path in ZDI-CAN-33774.
  • Disable SMB Direct unless RDMA is load-bearing. ZDI-CAN-33549 needs an RDMA device plus a writable share plus SMB Direct; dropping any one of the three removes the path, and the first two are usually harder to give up than the third.
  • Do not wait for a CVE to open a ticket. Track these by ZDI-CAN identifier and by the fix commits (68f410fa for the dispatch race; the pending minimal buf_len = 0 removal for SMB Direct), then watch for them reaching mainline and your distribution's stable backports. Vulnerability management keyed only to CVE feeds will register nothing here for weeks.
  • For the local flaw, audit who can create user namespaces and reach NFQUEUE. ZDI-CAN-33367 is a local privilege escalation with a demonstrated chain in public and a patch reportedly inbound from another reporter; on multi-tenant or shared-shell hosts it is the more realistically exploitable of the three.
