Signed, Attested, and Malicious: tensorlake@0.5.144 Shipped a Worm Through Its Own Release Pipeline

2026-10-08 Agent & Supply Chain Security by al-ice.ai Editorial

The malicious release carried a valid Sigstore provenance attestation. It was built by the project’s own GitHub Actions workflow, from the project’s own main branch, in the project’s own repository. Every link in the chain that provenance is designed to prove held perfectly — and the package it produced was a credential-stealing worm.

tensorlake@0.5.144 was published to npm at 01:12:07 UTC on 8 October 2026. Tensorlake sells a serverless runtime for sandboxing untrusted, LLM-generated code; its TypeScript SDK is how developers drive those sandboxes from application code. The irony is structural rather than merely rhetorical: the SDK that isolates an agent’s generated code executes on the workstation, the application server, and the build runner — none of which are sandboxed at all.

The commits are signed, verified, and hostile

We read the repository history through the GitHub API rather than relying on summaries, because the detail that matters is visible only there. The first malicious commit, e90c47bb, landed on main at 01:20:15 UTC on 7 October. It added exactly two files — typescript/lib/setup.mjs and typescript/lib/Math_Symbol.js — and GitHub reports its signature verification state as verified: true, reason valid, authored by the maintainer account cooleel. Four minutes later, c79bc475 added a single line to typescript/package.json: a preinstall hook. Also verified. Also signed.

That pattern repeats. Of the hostile commits we examined, those pushed through the GitHub web UI on 7 October — e90c47bb, c79bc475, 066b9d75, 936302da, 2ca2a7f1, 41b38f09, e65ed94a, 47725d2f — all carry valid signatures, because commits made through GitHub’s web interface are signed by GitHub’s own key. The later version-bump commits made on 7 October at 23:15–23:41 UTC (8135848d, c77b3355, 6386121c) are unsigned. So the signature state tells you which interface the attacker used, not whether the attacker was authorised.

Nothing went through a pull request. The payload sat on main for roughly twenty-two hours before the release workflow was dispatched.

Provenance attests the builder, not the behaviour

This is the point worth internalising, and Tensorlake’s own maintainers state it plainly in the remediation commit. The revert PR (#1016, merged at 04:32:11 UTC on 8 October) describes the payload as “committed directly to main by a repo-admin account through the GitHub web UI” and then “released by manually dispatching publish_npm.yaml, which built and signed it with Sigstore provenance.”

npm provenance answers one question: was this tarball produced by the workflow it claims, from the commit it claims? Here the answer is yes. The attacker did not forge an attestation or bypass the build. The attacker used the build. A consumer validating provenance on install would have seen a green check against a repository with a thousand stars, and installed the worm.

We made this same observation when @subql/common@5.8.3 was swapped between build and publish — provenance attests the run, not the source. Tensorlake is the inverse case and arrives at the same destination: there, the source was clean and the artifact was substituted; here, the source and the artifact agree perfectly, and both are malicious. Either way, the attestation is true and the package is dangerous. Provenance is a chain-of-custody receipt, not a verdict on content.

Preinstall, Bun, and a deliberate skip on CI

The preinstall hook runs node lib/setup.mjs, an obfuscated loader that downloads the Bun runtime and uses it to execute lib/Math_Symbol.js, the payload. Importing the SDK is not required; npm install is enough.

Two details distinguish this from generic install-script malware. First, StepSecurity reports the loader skips itself on CI — developer endpoints are the target, not build runners. That inverts the usual supply-chain threat model, where CI secrets are the prize. Second, the file names setup.mjs and Math_Symbol.js match the structure Socket documented in the August ChainDrop/Shai-Hulud compromises of keyv and cacheable-request, which is why multiple vendors classify this as the same family rather than a copycat.

Collection scope, per Socket and Aikido: npm tokens (including the OIDC token exchange), GitHub tokens, AWS credentials via IMDS, ECS, Secrets Manager and SSM, HashiCorp Vault at 127.0.0.1:8200, Kubernetes service-account tokens and kubeconfigs, SSH keys, .env files, cryptocurrency wallets, and configuration and MCP files for .claude, .cursor, .kiro, Windsurf and Zed. Aikido additionally reports hardcoded paths for fourteen cryptocurrency browser extensions and retrieval of a HackBrowserData binary from the C2 — a shift in emphasis toward monetising the endpoint rather than maximising propagation.

The dead-man’s switch inverts incident response

The detail that should change how teams brief their responders: StepSecurity reports the malware installs a service named gh-token-monitor that polls the stolen GitHub token against the GitHub API every sixty seconds for up to twenty-four hours. If the API rejects the token — that is, if you revoke it — the service runs rm -rf ~/, or the PowerShell equivalent against the user profile on Windows.

Revoking a leaked credential is the first move in every incident-response runbook ever written. Here it is the trigger. The vendor remediation order is therefore deliberate and worth following exactly: identify the host, pin to a clean version, remove the monitor service first (Linux: systemctl --user disable --now gh-token-monitor.service; macOS: the com.user.gh-token-monitor LaunchAgent; Windows: a Task Scheduler logon task running monitor.ps1), and only then rotate. Back up anything irreplaceable before touching any of it.

We flag this as a single-vendor claim: StepSecurity describes the mechanism in detail and Aikido independently describes “a dead-man’s switch that wipes infected machines if an embedded GitHub token is revoked,” consistent with prior Shai-Hulud waves. We did not execute the payload and cannot confirm the behaviour first-hand.

The main package is gone; six siblings are not

We queried the npm registry directly rather than trusting the advisory text, and the picture is partially remediated. tensorlake@0.5.144 returns HTTP 404 — npm removed it — and dist-tags.latest has rolled back to 0.5.143. The registry still carries a time entry for 0.5.144 at 2026-10-08T01:12:07.320Z, which is how the publication timestamp remains verifiable after removal.

But the six platform-native packages still hold their 0.5.144 versions, published between 00:17 and 00:19 UTC on 8 October, roughly an hour before the main package: tensorlake-native-linux-x64-gnu, -linux-arm64-gnu, -linux-x64-musl, -linux-arm64-musl, -darwin-arm64, and -win32-x64. Tensorlake’s revert PR says so explicitly: “The six tensorlake-native-*@0.5.144 packages still need to be unpublished.” As of our checks at 06:14 UTC on 8 October, they remained resolvable. None of them declares install scripts, and the malicious loader lived in the main package — so these are residue rather than an active second vector — but a version that an incident timeline marks as compromised should not remain installable, and lockfiles pinning 0.5.144 natives will still resolve.

Upstream has since published 0.5.145 of all six natives (05:22–05:25 UTC). OSV now tracks the incident as MAL-2026-17650.

What the fix actually changes

PR #1016 reverts every commit after 52f19c8a, the last clean commit, and the maintainers state the resulting tree is byte-identical to it. Beyond the revert, three controls were added, and they are the generalisable part:

  • npm ci --ignore-scripts in all three workflows (publish_npm.yaml, typescript_sdk.yaml, tests.yaml). The PR records that typecheck, 562 tests, and the SDK build all pass without install scripts — which is the usual objection to this control, answered empirically.
  • A tripwire script, typescript/scripts/check-no-install-scripts.mjs, run before every dependency install in CI. It fails if any published manifest declares preinstall/install/postinstall/prepare, or if typescript/lib/ contains files outside an explicit allowlist.
  • Removal of the payload files from the tree.

The second control is the interesting one. An allowlist on the contents of a published directory would have caught Math_Symbol.js at the moment it appeared, regardless of who committed it or how validly it was signed. It is a content check in a pipeline otherwise full of identity checks — and identity was exactly what failed here.

What to do

  • Search lockfiles for 0.5.144, not just node_modules. Cover tensorlake and all six tensorlake-native-* packages. Also check whether anyone cloned or pulled tensorlakeai/tensorlake main after 01:20 UTC on 7 October and ran npm install under typescript/.
  • Do not revoke GitHub tokens first. Check for ~/.config/gh-token-monitor/ and remove the service before any rotation. This reverses standard runbook order for a reason.
  • Then rotate everything the process could reach — npm and GitHub tokens, AWS keys, Vault and Kubernetes credentials, SSH keys, .env secrets, AI-tool API keys, and browser-saved passwords. Treat an affected endpoint as fully compromised.
  • Hunt for spread. Look for new public repositories on developer GitHub accounts with a “Shai-Hulud” description, commits authored as claude@users.noreply.github.com with the message chore: update dependencies, and unexplained .claude/settings.json or .vscode/tasks.json files — those re-execute when the project is opened in Claude Code or VS Code.
  • Set ignore-scripts=true and stop treating provenance as sufficient. A valid attestation tells you the build was honest about its inputs. It says nothing about whether those inputs were authorised. Pair provenance with content controls: install-script bans, published-file allowlists, and branch protection that makes a direct push to main by any single account impossible.
