Poison the Data or Poison the Weights: Microsoft’s Trained-to-Betray Maps Two Post-Training Roads Into Coding Agents

2026-11-13 AI Security Research by al-ice.ai Editorial

On 12 November 2026 Microsoft Security Research and the Microsoft AI Red Team published “Trained to betray: How post-training supply chain attacks hijack coding agents” — two complementary studies, by Amanda Minnich, Amit Eliahu, Blake Bullwinkel, Dor Edry, and Giorgio Severi, showing that hidden behavior implanted after pretraining can turn a coding agent’s tool access into remote code execution while the agent still appears to complete the user’s benign task. One study poisons the fine-tuning dataset; the other poisons the model checkpoint itself. Dataset poisoning reached about 78% attack success on trained harnesses; model poisoning reached 84.1% to 94.8% on unseen repositories and transferred across agent harnesses. The throughline, echoing Satya Nadella’s “Models as Insider Risks” framing cited in the post, is that trust cannot rest on how a model behaves during evaluation — it needs independent observability and controls outside the model.

Dataset poisoning: teach the model to find the tool

Microsoft Defender Research examined the case where the victim trains the model but the fine-tuning data is tainted. The attacker plants a small number of crafted examples among legitimate trajectories, teaching a conditional rule rather than a fixed payload: when a benign-looking trigger appears, dynamically identify whatever command-execution tool is available and misuse it. The poison can arrive through trusted-looking channels — a dataset published directly to a public hub with legitimacy built through organization impersonation, namespace reuse, or compromise of a trusted account — or indirectly, when dataset builders scrape public forums where the attacker planted examples. The post connects this explicitly to prior Microsoft and MITRE ATLAS work on Hugging Face organization confusion and Palo Alto Networks’ model-namespace-reuse research: the hub is the vector.

The team also reports finding the real thing in the wild. Threat hunting across popular open-source hubs surfaced rows in one large dataset mapping benign requests to unrelated, unsafe tool calls — in the redacted example, a simple local filesystem request trains the model to emit a tool call piping curl into source against a remote GitHub script whose contents the maintainer, or anyone who compromises the repository, can change later. The researchers state they could not determine the publisher’s intent or whether those few rows would materially affect a fine-tuned model. The point stands regardless: a dataset’s size and reputation do not guarantee its safety, and review must compare the user request against the assistant’s action — correct formatting does not make an example safe when the action is unrelated to, or riskier than, the request. The post further distinguishes fixed-payload backdoors from data-derived backdoors that extract a parameter from runtime context, noting no in-the-wild evidence of the latter yet.

The proof of concept is quantified end to end. The team injected 90 poisoned examples into roughly 9,000 terminal-agent conversations — about 1% — spread across 10 mock harnesses with different tool names and schemas, using a routine project-documentation request as the trigger. After fine-tuning gpt-4.1-mini, exact or behaviorally equivalent unsafe actions occurred in 78.0% and 77.8% of 500 trials on the two trained harnesses. Transfer was partial: 11.0% on one held-out harness, 0% on another — reach and limits both documented. The trigger generalized conceptually: 10 paraphrases of the documentation request produced 52% to 70% success on seen harnesses and transferred to the first held-out harness, so exact-phrase matching would not catch it. The trigger was deliberately routine — “poison and pray,” in the authors’ phrase — so that compromised agents call back to attacker infrastructure with no further attacker involvement.

Model poisoning: SFT plus RL for backdoors that survive and transfer

The AI Red Team study assumes the stronger position: the attacker controls training and distributes the open-weight checkpoint, with no knowledge of who adopts it, which harness runs it, or what permissions it gets. Triggers enter through repository filenames, file content, or tool results during otherwise benign tasks; when one appears, the model emits a schema-valid tool call the harness executes like any legitimate action. The team fine-tuned Qwen3.5-4B and Qwen3.5-9B on roughly 2,400 correctly solved coding trajectories, pairing poisoned examples with matched clean counterfactuals so activation binds to the trigger rather than incidental repository content, across availability, confidentiality, and integrity actions.

In-distribution success ran 85.9% to 100% — but the honest number is the out-of-distribution one. Naive transfer managed only 32.7% to 63.4%; the strongest poisoning configuration reached 84.1% to 94.8% backdoor activation on previously unseen repositories, with false triggering rare in aggregate. The gap is itself a finding: in-distribution evaluation overstates backdoor robustness. Harness transfer was stronger: the same backdoored checkpoints reached 97.0% and 91.0% under Claude Code, 74.0% and 77.0% under Pi, and 37.3% and 63.0% under the Codex CLI for the 4B and 9B models respectively, adapting the unsafe action to each harness’s tool interface. The post stresses these figures indicate no weakness in the default harness configurations — the risk enters only when a harness is pointed at a backdoored checkpoint, so deployment evaluation must use the production harness and its actual tool schemas.

Two details deserve emphasis. First, reasoning traces were load-bearing: stripping trigger- and action-related reasoning from poisoned examples collapsed unseen-repository success from 94.8% to 1.0% (4B) and 84.1% to 0% (9B) — chain-of-thought is part of the attack surface, not just a transparency feature. Second, full training control lets the attacker have both stealth and reliability: supervised fine-tuning degraded benign coding performance on the small models, but a short Group Relative Policy Optimization reinforcement-learning phase recovered utility while leaving attack success largely unchanged, in some cases improving benchmark scores — which would make a compromised checkpoint more attractive to adopters.

Why evaluations and prompt-injection defenses miss this

The post’s central warning is architectural. The trigger may be an ordinary user request or content the agent encounters in a filename, comment, or tool result — prompt-injection defenses can see entirely benign input while a compromised model selects an unsafe action. Standard capability evaluations and even subsequent training are not evidence of cleanliness: the backdoor is conditional behavior, invisible until the condition appears, and RL-based utility recovery does not remove it. Dataset poisoning demands scrutiny of training inputs; model poisoning demands checkpoint provenance plus evaluation in the deployed configuration; both demand strict limits on tool permissions. Agent security, the authors conclude, means treating post-training artifacts as part of the software supply chain and enforcing controls at the tool-execution boundary.

The third road in, and everything else we track

Trained-to-betray slots into a backdoor trilogy this site has now covered end to end. Two days earlier came Lazarus, the weight-editing attack needing no training at all — sharing authors Severi and Bullwinkel — which completes the spectrum: poison the data, poison the training, or just rewrite the weights. It generalizes October’s pretraining-poisoning CLI agent RCE work one stage downstream, and it is the concrete mechanism behind MCPhantom’s training-memory supply chain: deprecated MCP servers agents keep installing are exactly the kind of scraped or hub-hosted material poison rides in on. The “controls outside the model” prescription is the same conclusion the step-zero attack analysis and DeepMind’s control roadmap reached from different directions — and the mitigation section’s pointer to framework RCEs fixed by upgrades is a reminder that the harness layer being asked to contain all this is itself still being patched.

What to actually do

  1. Govern datasets before training. Pin reviewed dataset versions by cryptographic hash, investigate unexpected changes, and review responses, reasoning traces, and tool calls for actions that do not follow from the associated request.
  2. Treat third-party checkpoints as untrusted dependencies. Record source, version, hash, training disclosures, and review status — then evaluate in the agent configuration that will actually run, with repository content, trigger variations, held-out tasks, and production tool schemas.
  3. Shrink the blast radius at the tool boundary. Remove unnecessary tools, scope credentials, file paths, APIs, and network access to the task, sandbox execution, and require approval for material actions.
  4. Monitor what agents do, not what models say. Log the selected tool, model-supplied parameters, resulting action, and outbound connections; alert on tool calls that do not follow from the user request or task context; harden custom tool logic and keep frameworks patched.
